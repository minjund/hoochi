# hoochi: notes for agents

- `plugin/` is the Claude Code plugin (a mod: `hooks/register.ts`). It writes what the window reads under `~/.hoochi/`.
- `app/` is the window: React in `app/src`, Tauri (Rust) in `app/src-tauri`.
- The main moments (chat start/end, prompt, before/after a tool, Stop, StopFailure, SubagentStart/Stop, Pre/PostCompact, PostModelSwitch) are served from Claude Code's own events (`prompt.submit`, `tool.call`, `turn.complete`, `agent.spawn`, `session.start`/`end`/`compact`), listed in `NATIVE` in `register.ts`. After changing model has no event of its own: the plugin compares the model at each prompt and puts its words in with the next one. On Team and Enterprise accounts the built-in `sec-default` plugin passes every `classic.*` event on beneath a person's plugins, so the classic hook only serves the moments in `CLASSIC_ONLY`, and hoochi does not hook the native ones so nothing goes in twice.
- Where the classic hooks never arrive (two answers in a row with no `classic.MessageDisplay`), the plugin writes `~/.hoochi/classic-claude.json` as `blocked`, and the window dims the `CLASSIC_ONLY` moments (kept in `app/src/lib/lifecycle.ts` too; `app/tests/reach.test.ts` checks the two lists match).
- hoochi was called hookwich before 0.1.28. The plugin moves `~/.hookwich` to `~/.hoochi` once (`moveOldFolder`) and shows a toast while `hookwich@hookwich` is still installed. The window points Codex hooks that run another copy at itself (`codex::repoint`), and still counts the entries and the plugin under the old name as its own. An old Hookwich window's Update button downloads `Hookwich-macos-<arch>.zip`, so every release also ships the same window zipped as `Hookwich.app` under that name; opened from `~/.hookwich/Hookwich.app`, the window moves the folder and itself to `~/.hoochi/Hoochi.app`, installs the hoochi plugin, removes the hookwich one and opens again (`app/src-tauri/src/rename.rs`). Chats opened before that keep the old plugin until they reload, so the old names stay as links: `~/.hookwich` → `~/.hoochi` (the plugin's move and the window both leave it; a `~/.hookwich` an old chat wrote again with records only is replaced by it) and `~/.hoochi/Hookwich.app` → `Hoochi.app` (the old plugin opens this window instead of downloading its own).

## The window's states

The window's flows are written out as pure functions in `app/src/lib/machines.ts`. Each one lists its states and what moves it from one to the next.

| Flow | States | On the page |
| --- | --- | --- |
| Saving your edits (`createSaver`) | saved, waiting, writing, failed | `.hw-panel[data-save]` |
| Updating hoochi (`updateFlow`) | unknown, current, available (+error), installing, reopening | `.hw-panel[data-update]` |
| The notice (`Notice`) | undo, error | `[data-notice]` |
| Asking before deleting many items (`askFlow`): a place's items or all of them | none, asking | `.hw-confirm[data-asking]` (`delete`) |
| Following where you chat (`followState`), always on with no switch | on, paused, held, busy (input reached two or more terminals within 20 s: a tool typing into terminals looks like you typing, so the window stays put; `noteInput` / `busyPlaces`); the tab goes to "this project" or "everywhere" | `[data-follow]` |
| Which screen | bubble, chat, picture, editor | `[data-view]` |

hoochi's question is "why doesn't my hook run?". The panel opens on the Lifecycle tab (below); the chat (`ChatView` in `components/hoochi/chat-view.tsx`) is the other tab: one box where you say what you want in your own words. The window asks this computer's Claude Code once (`ask_claude` in `app/src-tauri/src/understand.rs`: `claude -p` with no tools, MCP servers, settings or saved session, so no plugins or hooks run in it) with the instructions and answer shape built in `app/src/lib/understand.ts`, and shows one rule card (when, what, why) with its own button for each AI ("Put in Claude Code", "Put in Codex"), each undone on its own, or "Adjust" to open it in the editor (filled in, unsaved). The rule is made in Claude Code's moments, with the ones Codex has too marked; `ruleFor` in `understand.ts` turns it into the other AI's terms (Codex's hooks call any file edit `apply_patch`) or says why it cannot go in there (no such moment, or words do not reach it), and the button is dimmed with that note. Putting one in for Codex connects Codex's hooks if they are not yet. A terminal belongs to one AI, so for the other one a rule picked for "this terminal" goes in that terminal's project. A sentence can also act on the rules already put in, for both AIs and every place: everything the buttons do. The instructions list each rule with a short ref (`r1`…) and the places (`g`, `p1`…, `t1`…), and the answer's `action` is one of add, find (a list of the rules that match, each row with switch, adjust and delete buttons that act at once and can be taken back), change (one or several rules: their words, moment, tools, "only when it fails", "once", their place or their AI; `changes` has one entry per rule), copy (to another place or AI), off, on, delete (one, several or all). What the person said just before and the rules on the card it left on screen (`onLastCard` in `App.tsx`, `touched` in `edit.ts`) go in with the next sentence, so "turn these off" or "delete the second one" act on them. `interpret` in `understand.ts` checks the answer against those lists (refs never reach the person), `editOf` in `App.tsx` makes it concrete (where each one ends up, new ids for copies, copies already there left out), and the card shows what it touches (before and after for a change) with one button; `applyEdit` / `revertEdit` in `app/src/lib/edit.ts` do it and take it back without undoing anything else. When it is not clear which rule is meant, the answer asks which one. Each rule in the instructions carries how it is doing (`health` on `Known`: "works", "not working: …"), so a question why a rule does not run, or what is broken, is a find, and the find card shows each row's state and reason (`stateOf`). Without Claude Code (and in the browser demo) a few ready-made rules are matched by their words, and finding, switching off, on or deleting finds rules by their words, or takes "these" from the last card; "why doesn't … run?" finds the rule named, else the ones not working (`matchEdit`). Tabs at the top ("Lifecycle" with the number of rules and, in red, how many are not working / "Say it in words") switch between the lifecycle page and the chat.

Why a hook runs or does not (`app/src/lib/why.ts`, its words in four languages in `app/src/lib/why-words.ts`): `whyRule` goes through a rule's checks in the order the plugin makes them (on, its AI connected or the plugin heard from, the moment came (`seen`) or is blocked, it reaches the chat in view or a narrower place hides it, its tools against the tools that came (case, `|` in a name, the other AI's names), words at a moment where nothing reaches the model, how its last run ended (`runs`)); `whyOutside` does the same for a hook set up outside hoochi (on, its matcher against the tools that came, its last runs as Claude Code recorded them). The first failing check is the reason; `isTrouble` (stuck or failing) is what "not working" collects. The plugin (`noteRuns`, `noteSeen` in `register.ts`) and the Codex hook (`note_runs`, `note_seen` in `codex.rs`) write `runs` (each item's runs: count, failures, the last one and the last failure, with exit code, time and the start of what a failed command printed) and `seen` (each moment: when it last came and its latest tools) in `activity-<agent>.json`, merged with what other chats wrote. Claude Code records the settings and plugin hooks it runs in the chat's transcript: a `hook_*` attachment for most, and for the Stop hooks of a turn a `stop_hook_summary` listing them (only a failure gets an attachment of its own); async hooks leave no record; `app/src-tauri/src/hookruns.rs` (`hook_runs`) reads the newest transcripts from their end, only what each one gained since, and the window matches the runs to an outside hook by its command or its `statusMessage`. Codex records no hook runs, so an outside Codex hook is checked by its setup alone. `places.json` keeps the chat (`session`) running in each terminal.

The "Lifecycle" tab (`RuleList` in `components/hoochi/rule-list.tsx`, its data in `app/src/lib/rules-view.ts`) starts with the chat the window follows (its AI, place, how many rules go in there and how many are hidden) and the hooks not working, failing ones first, each with its reason (pressing one opens it), then the ways into the two lists and switching skills, then the lifecycle picture (`flowPicture` in `App.tsx`: the AI of that chat, or the one picked above the picture; its boxes count what goes in at that chat, grey numbers count hooks set up elsewhere, Claude Code's shows the context window; resting on a box shows what it holds, at the start of a chat the context it loads with the skills switch; pressing a box opens that moment in the editor). The lists open in popups (`RuleList` with `part` "rules" or "outside", modals `rules` and `outside`); a rule's or a hook's popup opened from one goes back to it when closed (`listBack`). "What you put in" lists every rule for both AIs at every place in one list, by moment in the order a chat goes through them (`momentOrder`: Codex's own moments in their place, marked "Codex only"), one row per rule with its AI (a colored dot), its place and its tags. The switch beside that heading shows everything (the default) or only what goes in at the chat in view. A row a narrower place hides (the narrowest place with a filled item at that moment wins: `decidingScope`, `pick` in the plugin and in `codex.rs`; a switched-off item still claims its place, an empty one does not, so a place with nothing set follows the wider one) says so in either view, with the place that wins and "Put it in there too"; each row says when it last ran (by item id in `activity.recent`). "Not working" collects hidden rows, Codex rules while Codex is not connected (a bar above offers to connect it), and Claude moments this account never gets. A search box and chips filter by AI, place, off and not working. Pressing a row opens it in a popup: every check it went through and what a failed run printed (`WhyPanel` in `components/hoochi/why-panel.tsx`), then `ItemCard` from `slot-editor.tsx`, at the rule's own AI and place (what it puts in, only when it fails, tools, once, on or off; Save writes it). Each row switches on and off in place; its menu sets it in the popup, changes it in words (the chat opens with the rule on a card, so the next sentence acts on it), opens the editor at the rule's own AI and place, puts it in other places (the send sheet) or in the other AI, or deletes it with an undo. Adding is done in words; "Make one yourself" opens `MomentPicker` and then the editor, which keeps the AI and place controls (they show only while the editor is open). "Hooks set up elsewhere" lists the hooks in settings files and plugins with how their last runs ended; pressing one opens its checks, what it runs and its switch. Each item in the editor ends with a one-sentence preview of what it will do (`t.preview`). Copying goes one way, out: "Send all of this place" (above the editor) and "Put in other places too" on each saved item open the same sheet (what, then where).
| The popup (`Modal` in App.tsx) | mine, skills, send, pick, rules (what you put in), outside (hooks set up elsewhere), rule (one rule set from the Lifecycle list), hook (a hook set up elsewhere, with its checks), none | `.hw-panel[data-modal]` |
| An item being edited (`ItemCard` in slot-editor.tsx) | saved, unsaved (Save writes it) | `.hw-item[data-unsaved]` |

Rules these flows keep:

- One write at a time.
- A failed save stays on screen: the file on disk does not replace it until a retry writes it.
- An undo ends as soon as anything else changes the config.
- Deleting many items waits for a yes; any change to the config, the place or the popup ends the ask unrun. Deleting one asks once more in place (`ConfirmDelete` in `components/hoochi/confirm-delete.tsx`): a row of the Lifecycle list, the popup, the editor, a row of a find card and a delete card in the chat. Copying does not ask: the send sheet (`components/hoochi/send-sheet.tsx`) shows what will happen in one sentence before you put it in, and an undo follows.
- Only one popup is open at a time, and a notice shows inside it.

To add a state, change `machines.ts` first and add its case to `app/tests/machines.test.ts`.

## Checks

```sh
cd app && npm test && npx tsc -b && npx eslint src/App.tsx src/lib src/components/hoochi tests
cd app/src-tauri && cargo test
claude plugin test plugin && claude plugin validate plugin
```

`components/ui` is a vendored copy of affectUI and has lint errors of its own, so lint only the paths above.

The browser demo runs without Tauri and keeps everything in localStorage:

- `npx vite build`, then `python3 -m http.server <port> -d dist`
- Open `/?demo&panel&lang=ko`.
- Add flags as needed: `&update`, `&select=SessionStart`, `&agent=codex`, `&scope=project`, `&blocked` (classic hooks blocked, as on a Team account).
